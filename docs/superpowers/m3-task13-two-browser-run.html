The one condition that stops the run

A student returned to the teacher list while holding a paid session

If a payment succeeds and the student ends up back on /teachers rather than in the call — stop immediately and tell me. That is money taken with nothing delivered, and it is the single failure this whole milestone is built to make impossible.

Everything else is recoverable and worth finishing the run for. A row sitting at paid for more than a few seconds is the visible form of the same problem — watch-sessions prints a warning when it sees one.

The run

Seven scenarios. The first is the one that matters most; the rest are the ways it can go wrong. Two are marked new — they were built today and have never run in a browser.

  2. Student /find → CBSE · 11th · Science · Physics → Start now on Mr. Azad.

02

The student never pays

the teacher is released without a timer or a cron

Do this

  1. Request and accept as before.
  2. Student Do nothing at all. Watch the countdown run out.
  3. Teacher Confirm the waiting card clears and the toggle returns to Available now on its own.

The row must say

student screenreturns to the filtered teacher list
teacher screencard gone, available again, no clicking required
money₹— — nothing charged, nothing to refund
Expect the stored status to lag, and don't call it a failure. watch-sessions will keep showing accepted at 0s to pay. Only acceptSession writes payment_expired back, so the column settles the next time this teacher accepts anything. The screens are already correct — that is the read-time rule working as designed.
03

Back out of checkout, then pay

a second charge is never opened for one session

Do this

  1. Request, accept, then Student tap Pay.
  2. On Razorpay's page, press the browser back button instead of paying.
  3. Tap Pay again and complete it this time.

The row must say

after backing outstill accepted, still chg✓ — the charge stayed open
second Payresumes the same charge, not a new one
outcomeactive, exactly ₹500 collected — never ₹1000
The amount is the assertion here. Two charges for one lesson is the failure mode; payment_ref is write-once in the database precisely to make it impossible.
04

A payment that failsfirst time

a declined payment is not a lost session

Do this

  1. Request, accept, tap Pay.
  2. Use failure@razorpay so the payment is declined.
  3. Return and pay properly, if the window is still open.

The row must say

after failurestill accepted — a failed payment changes nothing
money₹—, no refund reference
retryworks, and reaches active normally

presence follows the commitment, not the navigation

  2. From a third browser or window, send a request as any student and have the teacher accept it.

If you only have two browsers, skip step 2's third party and just watch the teacher's own toggle go amber on accept and back to green on expiry. That proves the same mechanism, one side of it.
07

Pay and cancel at the same instant

the only race in the system that can lose money

Do this

  1. Request, accept, and open checkout in one tab.
  2. Open the waiting screen in a second tab of the same browser.
  3. Complete the payment, and hit Cancel in the other tab at the same moment.
  4. Check the Razorpay dashboard afterwards either way.

Exactly two outcomes are acceptable

cancel lostactive — the student lands in the call, and Cancel reports it could not cancel
cancel woncancelled and a refund appears in Razorpay
anything elsestop — see the condition at the top of this page
This is the one worth doing deliberately. The refund arm has never executed against a real captured payment — the adapter resolves the pay_… id from the plink_… id at refund time, and only a genuine payment proves that path.
